## 1. 目标

项目里的统一通知服务地址：

- `http://localhost:28004`

接口：

- `POST /notifications/publish`：普通通知
- `POST /notifications/center`：中屏确认弹窗
- `POST /notifications/center/respond`：中屏确认弹窗回执，通常由前端自动调用
- `GET /notifications/history`：通知历史
- `GET /notifications/stream`：SSE 实时订阅
- `GET /health`：健康检查

---

## 2. 整体链路

### 2.1 普通通知

后端或前端调用：

`POST /notifications/publish`

通知服务处理后会：

1. 写入普通通知历史。
2. 通过 `GET /notifications/stream` 推送 `notification` 事件。
3. 前端右上角显示通知卡片。
4. 用户可打开右侧通知中心抽屉查看历史。

### 2.2 中屏确认弹窗

后端或前端调用：

`POST /notifications/center`

通知服务处理后会：

1. 通过 `GET /notifications/stream` 推送 `notification_center` 事件。
2. 前端在屏幕中央显示确认/拒绝弹窗。
3. 用户点击确认、拒绝，或超时自动关闭后，前端调用 `POST /notifications/center/respond` 回执。
4. 原始 `POST /notifications/center` 请求在收到回执后才返回。

返回结构固定为：

```json
{
  "result": "ok",
  "user": "admin"
}
```

其中：

- `ok`：用户点击确认
- `bad`：用户点击拒绝
- `timeout`：超时关闭，或未登录用户被前端直接过滤

---

## 3. 后端如何接入

### 3.1 适用场景

后端服务需要在以下情况主动发通知时，直接调用通知服务接口：

- 算法完成、保存成功、状态变化
- 外部接口异常、依赖服务离线
- 需要用户确认后再继续的动作
- 例如 `map_marker_service` 在路径规划、圆形/多边形/点位新增、路网加载保存、禁行区同步完成后，会直接向通知服务发普通通知

### 3.2 调用普通通知

请求示例：

```json
{
  "type": "notify",
  "method": "planning",
  "title": "任务完成",
  "message": "任务方案已生成",
  "source": "task_planning_service"
}
```

字段说明：

- `type`：通知等级，推荐值 `message` / `notify` / `emergency`
- `method`：可选，用于告诉前端这条通知要跳转到哪个模块
- `title`：可选，通知标题
- `message`：必填，通知正文
- `source`：可选，通知来源

其中 `method` 目前可映射到以下目标：

- `map`
- `situation`
- `decision`
- `planning` 或 `task_planning`
- `resource` 或 `resource_apply`
- `vehicle` 或 `vehicle_health`
- `settings` 或 `system-settings`

Python 示例：

```python
import requests

payload = {
    "type": "notify",
    "method": "planning",
    "title": "任务完成",
    "message": "任务方案已生成",
    "source": "task_planning_service",
}

resp = requests.post(
    "http://localhost:28004/notifications/publish",
    json=payload,
    timeout=5,
)
resp.raise_for_status()
print(resp.json())
```

FastAPI 服务内建议封装一个小函数统一调用，避免每个业务点直接写裸请求。

### 3.3 调用中屏确认弹窗

请求示例：

```json
{
  "type": "emergency",
  "title": "连接异常",
  "message": "是否重新建立连接？",
  "allowstr": "重连",
  "denystr": "取消",
  "source": "vehicle_control_service",
  "displaytime": 10
}
```

字段说明：

- `type`：通知等级
- `title`：必填，弹窗标题
- `message`：必填，弹窗正文
- `allowstr`：可选，确认按钮文案，默认 `确认`
- `denystr`：可选，拒绝按钮文案，默认 `拒绝`
- `source`：可选，来源，空值时前端不显示
- `displaytime`：可选，秒数，默认 `5`

Python 示例：

```python
import requests

payload = {
    "type": "emergency",
    "title": "连接异常",
    "message": "是否重新建立连接？",
    "allowstr": "重连",
    "denystr": "取消",
    "source": "vehicle_control_service",
    "displaytime": 10,
}

resp = requests.post(
    "http://localhost:28004/notifications/center",
    json=payload,
    timeout=11, # 一般来讲要比 displaytime 大点, 防止页面弹窗还未关闭请求就已经超时.
)
resp.raise_for_status()
result = resp.json()

if result["result"] == "ok":
    print("用户确认")
elif result["result"] == "bad":
    print("用户拒绝")
else:
    print("超时或当前前端未登录")
```

注意：

- 这个接口不是立即返回，而是会等待前端回执。
- 如果当前前端没有登录用户，前端不会显示中屏弹窗，会直接回传 `timeout`。
- 不要把长时间业务锁死在同步等待上，必要时应在业务层设置超时和降级策略。

### 3.4 后端接入建议

- 不要让每个 service 各自维护 SSE、浏览器弹窗或 WebSocket 连接，统一只调通知服务 HTTP 接口。
- 普通状态提示优先用 `/notifications/publish`。
- 只有确实需要用户明确确认/拒绝时，才用 `/notifications/center`。请注意, 不要轻易使用这个接口，因为它会阻塞业务流程并且影响体验.
- 后端如果只是上报失败、告警、服务离线，推荐统一跳转到系统设置页，对应 `method = "settings"`。

## 4. 前端如何接入

### 4.1 当前项目内的接入点

当前前端已经在全局挂载通知中心：

- `frontend/src/App.vue`
- `frontend/src/features/mission-control/shared/notifications/MissionNotificationCenter.vue`
- `frontend/src/utils/notificationCenter.js`
- `frontend/src/config/systemSettings.js`

其中：

- `App.vue` 负责全局挂载通知中心组件。
- `MissionNotificationCenter.vue` 负责显示右上角通知卡片、右侧历史抽屉、屏幕中央确认弹窗。
- `notificationCenter.js` 负责给业务模块提供统一调用入口。
- `config/systemSettings.js` 负责通知服务地址和接口路径配置。

### 4.2 前端推荐调用方式

业务代码不要直接操作 SSE，也不要直接在各组件里手写通知请求。统一从下面这个文件导入：

`frontend/src/utils/notificationCenter.js`

常用方法：

- `publishNotification(payload, options)`：发送普通通知
- `publishCenterNotification(payload, options)`：发送中屏确认弹窗
- `reportInterfaceIssue(payload)`：上报接口异常类通知
- `toggleNotificationCenter()`：打开或关闭右侧通知中心
- `openNotificationCenter()`：主动打开通知中心

### 4.3 发送普通通知

示例：

```js
import { publishNotification } from '../utils/notificationCenter';

await publishNotification({
  type: 'notify',
  title: '保存成功',
  message: '任务草案已保存',
  source: 'task-right-panel',
  method: 'planning',
});
```

说明：

- 服务在线时，前端会走后端通知服务。
- 服务离线时，默认会退化为本地通知卡片，不阻塞主流程。

### 4.4 发送中屏确认弹窗

示例：

```js
import { publishCenterNotification } from '../utils/notificationCenter';

const result = await publishCenterNotification({
  type: 'emergency',
  title: '连接异常',
  message: '是否重新建立连接？',
  allowstr: '重连',
  denystr: '取消',
  source: 'mission-chat',
  displaytime: 10,
});

if (result?.result === 'ok') {
  // 用户确认
}
```

说明：

- 请在必要时使用，请勿随便调用这个接口, 避免阻塞业务流程!!!
- 这个方法会等待后端 `/notifications/center` 返回。
- 服务离线时，默认退化为前端本地中屏弹窗。
- 如果当前没有登录用户，前端不会弹中屏提醒，而是直接走 `timeout`。

### 4.5 上报接口异常

如果你的模块只是想通知“接口不可用”“健康检查失败”“服务离线”，优先使用：

```js
import { reportInterfaceIssue } from '../utils/notificationCenter';

await reportInterfaceIssue({
  title: '车辆接口异常',
  message: '车辆控制服务暂不可用',
  source: 'vehicle-control',
  cooldownKey: 'vehicle-control-health',
});
```

这样做的好处：

- 自动走统一通知中心
- 自动带节流，避免轮询时刷屏
- 默认把跳转目标指向系统设置页

### 4.6 配置项

通知中心相关配置在：

- `frontend/src/config/systemSettings.js`

关键字段：

- `notificationBaseURL`
- `endpoints.notificationPublish`
- `endpoints.notificationCenter`
- `endpoints.notificationCenterRespond`
- `endpoints.notificationHistory`
- `endpoints.notificationStream`

默认值分别对应：

```text
http://localhost:28004
/notifications/publish
/notifications/center
/notifications/center/respond
/notifications/history
/notifications/stream
```

## 5. 如何替换浏览器默认通知

### 5.1 不再推荐使用的方式

以下方式不建议继续在项目里扩散：

- `window.alert(...)`
- `window.confirm(...)`
- `new Notification(...)`
- `Notification.requestPermission()`

原因：

- 样式不统一，和 MissionControl 的视觉体系割裂
- 浏览器通知依赖权限，用户体验不可控
- 系统通知无法天然联动项目内跳转、通知历史、统一过滤策略
- `alert/confirm` 会阻塞页面线程，交互体验差

### 5.2 替换关系

建议按下面的关系替换：

- `alert("xxx")` -> `publishNotification({ message: "xxx" })`
- `confirm("xxx")` -> `publishCenterNotification({ title: "...", message: "..." })`
- `new Notification("标题", { body: "内容" })` -> `publishNotification({ title: "标题", message: "内容" })`

对应示例：

```js
// 不推荐
alert('保存成功');

// 推荐
await publishNotification({
  type: 'notify',
  title: '保存成功',
  message: '任务草案已保存',
  source: 'task-right-panel',
});
```

```js
// 不推荐
const ok = window.confirm('是否删除当前任务？');

// 推荐
const result = await publishCenterNotification({
  type: 'emergency',
  title: '删除确认',
  message: '是否删除当前任务？',
  allowstr: '删除',
  denystr: '取消',
  source: 'task-board',
  displaytime: 10,
});

if (result?.result === 'ok') {
  // 执行删除
}
```

```js
// 不推荐
new Notification('连接异常', { body: '车辆控制服务已断开' });

// 推荐
await publishNotification({
  type: 'emergency',
  title: '连接异常',
  message: '车辆控制服务已断开',
  source: 'vehicle-control',
  method: 'settings',
});
```

### 5.3 推荐替换原则

- 只是提示用户看到即可：用普通通知
- 需要用户显式确认或拒绝：用中屏确认弹窗, 注意: 不要轻易使用这个接口，因为它会阻塞业务流程并且影响体验.
- 服务异常、地址错误、健康检查失败：优先用 `reportInterfaceIssue`
- 不要再在业务组件里直接请求浏览器通知权限

## 6. 最小接入清单

### 6.1 后端模块

如果一个新的后端 service 需要接入通知中心，最少做这些事：

1. 确定通知服务地址。
2. 在需要提示的位置发 `POST /notifications/publish`。
3. 在需要确认的位置发 `POST /notifications/center`。
4. 做好超时和失败降级，不要把主业务无限阻塞。

### 6.2 前端模块

如果一个新的前端模块需要接入通知中心，最少做这些事：

1. 从 `frontend/src/utils/notificationCenter.js` 导入工具函数。
2. 普通提示调用 `publishNotification(...)`。
3. 确认弹窗调用 `publishCenterNotification(...)`。
4. 接口异常优先调用 `reportInterfaceIssue(...)`。
5. 不再直接使用 `alert`、`confirm`、`Notification`。
