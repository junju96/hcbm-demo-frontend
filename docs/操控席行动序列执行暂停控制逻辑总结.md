# 操控席行动序列【开始/暂停/继续/停止】控制逻辑总结

> 整理日期：2026-09-01
> 范围：操控席行动序列（`action-sequence-control` 子视图）的执行控制全链路，供其它模块参考
> 事实来源：`src/features/mission-control/modules/coordination/panels/right/ActionSequencePanel.vue`、`src/features/mission-control/modules/coordination/api/coordinationApi.js`、`backend-dev/app/routers/action_sequence.py`、`backend-dev/app/services/action_sequence_client.py`、`backend-dev/app/services/task_monitoring_client.py`、`backend-dev/app/services/zenoh_client.py`

## 1. 总览：三段式控制链路

```
前端按钮 executeControl(actionType, [vid])
    │  POST /api/v1/action-sequences/operator/plans/{planId}/{start|pause|resume|stop}?vehicle_vid=xxx
    ▼
后端路由 action_sequence.py（:564-631）
    │  ① 状态机转移/重置（ActionSequenceRuntime.transit / reset）
    │  ② Zenoh control_mission 下发（task_control: 1开始/2暂停/3继续/4停止）
    │  ③ 任务监控联动（start→启动轮询；stop→停止轮询；pause/resume→不动）
    ▼
前端收到结果 → 校验 ApiResponse 信封 code → 2 秒后刷新列表和详情
```

## 2. 前端按钮层（ActionSequencePanel.vue）

- 操控席模式判定：`isControlMode = subviewId === 'action-sequence-control'`（:470）
- 按钮渲染在**每辆车卡片头部** `.as-vehicle-controls`，仅 `isControlMode && canOperateVehicle(vehicle)` 时渲染（:103-121）；顶部全局按钮区只有"发布为正式行动方案"（:66-76）
- `canOperateVehicle`（:597-607）：操控席要求已连接车辆（`isVehicleConnected`）且该车 vid 去 `equipment:` 前缀后等于 `connectedVehicleId`
- 按钮按该车运行时状态分支显示（`getVehicleRuntimeState`，:1205-1215）：

| 运行时状态 | 显示按钮 |
|---|---|
| SCHEDULED | 开始 |
| ACTIVE | 暂停 + 停止 |
| PAUSED | 继续 + 停止 |
| DONE | "已完成"徽标，无按钮 |

- 所有按钮 `:disabled="controlLoading"` 防重入
- 点击直连 `executeControl('start'|'pause'|'resume'|'stop', [vehicle.vid])`（:106/:109/:112/:118）

**注意：`getVehicleRuntimeState` 不读 plan 级 `runtime_state`，而是从该车 `vehicle_summary` 的 action 状态推断**（全 DONE→DONE；有 ACTIVE→ACTIVE；有 PAUSED→PAUSED；否则 SCHEDULED）。

## 3. executeControl（:1667-1722）—— 可复用模式

```js
// 1. 按席位选 API 函数（操控席带 vid 参数，协同席不带）
const apiFn = isControlMode.value ? startOperatorPlan : startActionSequence; // 以 start 为例
// 2. 多车并行，vid 去 equipment: 前缀
const results = await Promise.all(vids.map((vid) => apiFn(planId, vid?.replace('equipment:', '') || vid)));
// 3. 信封判定：HTTP 200 也可能业务失败
const isBizOk = (r) => r.ok && ((r.data?.code) ?? 200) === 200;
// 4. 全部成功 → 系统消息 + 2 秒延迟刷新（等 DS 行动状态推进）
setTimeout(() => { loadPlans(true); if (selectedPlanId.value) selectPlan(selectedPlanId.value); }, 2000);
```

要点：**HTTP 200 不代表业务成功，必须看 ApiResponse 信封的 `code`**；控制后给 DS 2 秒再刷新，避免读到未推进的旧状态。

## 4. 前端 API 层（coordinationApi.js）

操控席四个函数均为 POST 空 body，vid 走 query string：

| 函数 | URL | 行号 |
|---|---|---|
| `startOperatorPlan(planId, vehicleVid)` | `POST /api/v1/action-sequences/operator/plans/{id}/start?vehicle_vid=...` | :518 |
| `pauseOperatorPlan` | `.../pause` | :525 |
| `resumeOperatorPlan` | `.../resume` | :532 |
| `stopOperatorPlan` | `.../stop` | :539 |

协同席对照组 `startActionSequence` 等在 :386-407（无 operator 前缀、无 vid）。

## 5. 后端路由层（action_sequence.py）

| 端点 | 状态机操作 | Zenoh task_control | 监控联动 |
|---|---|---|---|
| start（:564-583） | `transit → ACTIVE`，失败 400 | 1 | 下发成功后 `start_monitoring` 启动轮询 |
| pause（:586-596） | `transit → PAUSED` | 2 | 不停轮询 |
| resume（:599-609） | `transit → ACTIVE` | 3 | — |
| stop（:612-631） | `reset`（无条件回 SCHEDULED） | 4 | `stop_monitoring` 停轮询 |

- 协同席对照组（:222-285）逻辑相同但**无任务监控联动**
- 前置下发端点 `POST .../operator/plans/{id}/dispatch`（:391-454）：先同步 plan 到操控席 DS，再发 Zenoh `MissionService/send_mission`，成功后 `register_mission_for_monitoring` 注册并推送预检冲突

## 6. ActionSequenceRuntime 状态机（action_sequence_client.py:1238-1346）

- 状态集合：`SCHEDULED / ACTIVE / PAUSED / DONE / DELETED`
- 转移表：SCHEDULED→{ACTIVE}；ACTIVE→{PAUSED,DONE,SCHEDULED}；PAUSED→{ACTIVE,SCHEDULED,DONE}；DONE→{SCHEDULED}；DELETED→∅
- `transit` **幂等**：已是目标状态直接成功；非法转移返回 False → 路由转 400
- `init_state_from_plan` **指纹重推断**（:1305-1346）：以 action 状态集合 `frozenset` 为指纹；指纹未变不覆盖用户已触发的控制操作；进行中状态（ACTIVE/PAUSED）只在行动全 DONE 时允许被指纹覆盖，防止 DS 行动状态未推进时把 ACTIVE 冲回 SCHEDULED
- 每次读详情时调用（协同席 `get_plan_detail` :494；操控席 `get_plan_detail_operator` :2617）

## 7. Zenoh 下发（control_mission）

- topic：`op/t01/g01/v{vid}/cmd/MissionService/control_mission`（vid 优先入参，否则取 plan 首车；均去 `equipment:` 前缀）
- payload：`{"service": "MissionService", "action": "control_mission", "args": {"taskid": tid, "aid": 0, "task_control": 1/2/3/4, "action_control": 0}}`（`build_control_mission_payload`，:2298-2331）
- `tid` 由 plan_id 数字提取或 md5 兜底（`_plan_id_to_tid`，:2253-2259）
- **Zenoh 失败不影响 HTTP 状态码**，成败在 `data.zenoh.ok`（`publish_control_mission`，:2334-2361）

## 8. 任务监控联动（task_monitoring_client.py）

- 总开关 `MONITORING_ENABLED`（app/config.py，**当前 False**），注册与轮询入口都会检查；细分开关 `MONITORING_PRECHECK_ENABLED`、`MONITORING_ROUTE_REGISTER_ENABLED`
- 下发时注册（黄色接口，一次）：超时检测注册 + 路线注册 + 出发前冲突预检 → `http://25.11.1.178:28509`
- start 后轮询（绿色接口）：`threading.Timer` 守护线程，**间隔 10 秒**（`POLL_INTERVAL_SECONDS`，:38），每轮依次：行动状态上报 → 位置上报 → 临机预警 → 偏离检测；任务全完成或各检测源都报过一次后自动停止；同类预警 60 秒节流
- **pause 不停轮询**；只有 stop 和任务完成自停

## 9. 状态回传前端

- plan 级：详情路由合并 `detail["runtime_state"] = action_runtime.get_state(plan_id)`（:386-387），含 `state/started_at/paused_at/updated_at`（剔除内部 `_fingerprint`）
- action 级：**后端不回写 action 状态**；`vehicle_summary` 中 action 的 `state` 来自操控席数据服务器的 plan 文档本身，状态推进依赖车端/外部服务写 DS
- 实时性：SSE `/api/v1/action-sequences/events` 推送 DS plan 变更；控制指令后前端另有 2 秒延迟手动刷新兜底

## 10. 参考要点与已知坑

**可复用模式：**
1. 前端：`executeControl` 的"信封 code 判定 + Promise.all 并行 + 2 秒延迟刷新"
2. 后端：`transit/reset → publish_control_mission → 监控联动`三段式
3. 状态显示从 DS 数据推断（`getVehicleRuntimeState`），不维护前端本地状态

**已知坑：**
1. `onStart/onPause/onResume/onStop` 包装函数与多车选择弹窗（:216-244）是**死代码**，现行 UI 只有单车按钮
2. 监控轮询实际 10 秒，注释/旧文档中的"每 5 秒"已过时
3. Zenoh 下发失败时 HTTP 仍 200，需看 `data.zenoh.ok`
4. action 状态不回写，按钮状态完全依赖 DS 数据推进——联调时若按钮不切换，先查 DS 里的 action.state
