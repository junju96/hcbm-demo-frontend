# 行动序列模块接口交互说明

> 版本：基于当前 `dev/action-sequence-params` 分支代码（含 Zenoh 通知 + SSE 实时刷新、数据服务器直取、import 全量保存等改动）  
> 适用范围：前端 `ActionSequence*.vue` / `coordinationApi.js`，后端 `action_sequence.py` / `action_sequence_client.py` / `data_server_client.py` / `sse_manager.py` / `zenoh_client.py`

---

## 1. 概述

行动序列模块（Action Sequence）是协同指控模块（Coordination）的子视图，同时服务两种运行模式：

- **协同席模式**：操作员通过协同席数据服务器查看、编辑、下发行动方案；
- **操控端模式**：车辆操控端在本地维护一份行动方案，可编辑参数、控制单车执行、并通过 Zenoh 将任务下发到无人车。

模块涉及四类后端服务：

| 服务 | 生产环境地址 | 开发环境代理 | 说明 |
|---|---|---|---|
| 协同席数据服务 | `http://25.11.1.222:28600` | `http://localhost:28600/api` | 方案、行动、车辆资源统一接口 |
| 操控端本地服务 | 同上（前缀 `/api/v1/action-sequences/operator`） | 同上 | 操控端本地 task_pool / 执行控制 |
| 地图服务 | `http://25.11.1.178:28001` | `http://localhost:5173/map` | 路线、区域、多边形上图 |
| 车辆控制服务 | `http://25.11.1.178:28009` | - | 用户登录状态、健康检查 |
| 上游车辆管理服务 | `http://25.11.1.147:28410` | - | 车辆实时信息（VMF、IP、类型） |

> **重要说明**：本后端服务（端口 28600）对大部分行动序列接口仅做"协议适配/中转"。收到前端请求后，它会向真正的**数据服务器**（协同席：`25.11.1.178:28801`；操控席：`25.11.1.56:28801`）发起二次调用，再把结果转换后返回给前端。车辆资源则来自**资源池服务**（`25.11.1.178:28800`）。车辆实时信息（VMF、IP、在线状态）来自**车辆控制服务**（`25.11.1.178:28009`），用于任务下发时的车辆寻址。

HTTP 统一由 `coordinationApi.js` 中 `safeFetch` 封装，默认 8 秒超时，统一返回结构：

```ts
{ ok: boolean; error: string | null; data: any }
```

## 2. 后端服务与数据服务器交互总览

| 后端文件 | 职责 |
|---|---|
| `app/routers/action_sequence.py` | FastAPI 路由层，接收前端请求，调用 Service 层 |
| `app/services/action_sequence_client.py` | 业务逻辑层：查询/转换/同步 plan，构造 mission_data，维护运行时状态 |
| `app/services/data_server_client.py` | 数据服务器 HTTP 客户端：封装 `_http_get/post/patch` 及操控席/资源池版本 |
| `app/services/task_pool.py` | 本地内存缓存（task_pool），用于 fake 调试和本地 dirty 数据兜底 |

### 2.1 数据服务器地址配置

```python
# app/services/data_server_client.py
DATA_SERVER_BASE_URL = "http://25.11.1.178:28801"          # 协同席数据服务器
OPERATOR_DATA_SERVER_BASE_URL = "http://25.11.1.56:28801"  # 操控席数据服务器
RESOURCE_POOL_BASE_URL = "http://25.11.1.178:28800"        # 资源池服务
```

### 2.2 核心数据服务器接口

| 数据服务器接口 | 用途 |
|---|---|
| `POST /api/v1/task_pool/resources/query` | 按 `task_type` 查询资源列表（PLAN / CAR_ACTIONS / ACTION / ROUTE / AREA / TARGET / EQUIPMENT 等） |
| `GET  /api/v1/task_pool/resources/simple/{rid}` | 获取单个资源详情（业务字段投影） |
| `POST /api/v1/task_pool/ingestion/import` | 全量导入/更新资源（upsert） |
| `POST /api/v1/task_pool/ingestion/forward` | 将资源下发到指定目标席位 |
| `POST /api/v1/task_pool/resources/{rid}/delete` | 级联删除资源及其子资源 |
| `GET  /api/v1/resource_pool/resources` | 从资源池查询 online equipment |

## 4. 详细接口说明

### 4.1 方案列表查询

#### 4.1.1 协同席：获取行动方案列表

- **前端调用时机**：
  - 组件 `onMounted` 初始化；
  - 用户点击"刷新"按钮；
  - 通过 SSE 接收 Zenoh 通知后自动刷新（替代原 5 秒轮询）。
- **前端接口**：
  ```http
  GET /api/v1/action-sequences/plans
  ```
- **后端处理函数**：`action_sequence.py::list_plans` → `action_sequence_client.py::query_plans`
- **后端向数据服务器发起的二次请求**：
  ```http
  POST http://25.11.1.178:28801/api/v1/task_pool/resources/query
  Content-Type: application/json

  { "task_type": "PLAN", "limit": 200 }
  ```
- **数据服务器返回**：PLAN 资源数组（可能包含 `plan_id / plan_title / stages / teams` 等字段）。
- **后端数据转换**：
  1. 调用 `_normalize_plan_field_names` 把数据服务器字段映射为本地字段（如 `plan_title→title`、`team_equipments→vehicles`）；
  2. **不再回退本地 task_pool，不再合并本地 fake 调测方案**，列表数据只从协同席数据服务器拉取；
  3. 提取 `plan_id / resource_id / title / state / teams_count / stages_count` 返回前端。
- **返回前端结构**：
  ```json
  {
    "code": 200,
    "data": {
      "items": [
        {
          "plan_id": "PLAN_20260511_001",
          "resource_id": "plan:PLAN_20260511_001",
          "title": "进攻战斗命令-行动方案",
          "state": "DRAFT",
          "stages_count": 4,
          "teams_count": 2
        }
      ],
      "total": 1
    }
  }
  ```
- **完成功能**：
  - 从协同席数据服务器加载全部 PLAN 资源，转换为前端列表。

#### 4.1.2 操控端：获取行动方案列表

- **前端调用时机**：同 4.1.1，仅在 `isControlMode === true` 时调用。
- **前端接口**：
  ```http
  GET /api/v1/action-sequences/operator/plans
  ```
- **后端处理函数**：`list_plans_operator` → `query_plans_operator`
- **后端向数据服务器发起的二次请求**：
  ```http
  POST http://25.11.1.56:28801/api/v1/task_pool/resources/query
  Content-Type: application/json

  { "task_type": "PLAN", "limit": 200 }
  ```
- **数据转换/返回**：与协同席逻辑一致，目标服务器改为操控席数据服务器；**不再回退本地 task_pool，不再合并本地 fake 调测方案**。
- **完成功能**：加载操控端数据服务器上的行动方案。

### 4.2 方案详情查询

#### 4.2.1 协同席：获取方案详情

- **前端调用时机**：
  - 用户点击左侧方案列表某一项（`selectPlan`）；
  - 通过 SSE 接收 Zenoh `plan.updated` 通知后自动刷新（替代原轮询）；
  - 参数保存、编辑、追加、删除后主动刷新。
- **前端接口**：
  ```http
  GET /api/v1/action-sequences/plans/{planId}
  ```
- **后端处理函数**：`get_plan` → `get_plan_detail`
- **后端向数据服务器发起的二次请求**：
  ```http
  GET http://25.11.1.178:28801/api/v1/task_pool/resources/simple/plan:{planId}
  ```
- **数据服务器返回**：单个 PLAN 资源的业务字段投影，可能字段名与本地 mock 不一致。
- **后端数据转换关键步骤**：
  1. `_normalize_plan_field_names` 字段归一化；
  2. **不再使用本地 task_pool 缓存优先逻辑**，详情数据只从协同席数据服务器拉取；
  3. `_build_car_actions_from_plan` 将 `stages.team_actions` 转换为按车辆组织的 `car_actions`；
     - 若 `team_actions` 中 actions 为空，会再次查询数据服务器：
       ```http
       POST /api/v1/task_pool/resources/query
       { "task_type": "CAR_ACTIONS", "limit": 200, "filters": { "plan_id": "PLAN_xxx" } }
       ```
     - 若仍缺失，再查 ACTION 资源：
       ```http
       POST /api/v1/task_pool/resources/query
       { "task_type": "ACTION", "limit": 500, "filters": { "plan_id": "PLAN_xxx" } }
       ```
     - **新增**：若 `stages.team_actions` 整体为空，直接查询 CAR_ACTIONS 资源补全整个 plan 的车辆行动，并限制只补全 `plan.teams` 中列出的车辆（teams 为空时通过 ACTION 资源反查确认归属）；
  4. `_to_frontend_plan` 构造 `vehicle_summary`，并根据 `action_id / name / param` 推断标准 `action_type`。
- **返回前端结构示例（关键字段）**：
  ```json
  {
    "code": 200,
    "data": {
      "plan_id": "PLAN_20260511_001",
      "resource_id": "plan:PLAN_20260511_001",
      "title": "进攻战斗命令-行动方案",
      "state": "DRAFT",
      "teams": [...],
      "targets": [...],
      "stages": [...],
      "vehicle_summary": [
        {
          "vid": "equipment:UGV-001",
          "resource_type": "Fire-Support-UGV",
          "total_actions": 4,
          "stages": [...]
        }
      ],
      "runtime_state": { "state": "SCHEDULED" }
    }
  }
  ```
- **完成功能**：
  - 从数据服务器获取 PLAN 详情，转换为前端可渲染的 `vehicle_summary`。

#### 4.2.2 操控端：获取方案详情

- **前端接口**：
  ```http
  GET /api/v1/action-sequences/operator/plans/{planId}
  ```
- **后端处理函数**：`get_plan_operator` → `get_plan_detail_operator`
- **后端向数据服务器发起的二次请求**：
  ```http
  GET http://25.11.1.56:28801/api/v1/task_pool/resources/simple/plan:{planId}
  ```
- **数据转换**：与协同席一致；**不再使用本地 task_pool 缓存优先逻辑**，详情数据只从操控席数据服务器拉取。
- **完成功能**：加载操控端方案详情。

### 4.3 在线车辆查询

#### 4.3.1 协同席 / 操控端：获取已连接无人车列表

- **前端调用时机**：
  - 组件 `onMounted`；
  - 用户点击"刷新"；
  - 切换到操控端模式时（`watch(isControlMode)`）。
- **前端接口**：
  ```http
  GET /api/v1/action-sequences/vehicles
  GET /api/v1/action-sequences/operator/vehicles
  ```
- **后端处理函数**：`list_online_vehicles` / `list_online_vehicles_operator` → `query_online_vehicles` / `query_online_vehicles_operator`
- **后端向资源池服务发起的请求**：
  ```http
  GET http://25.11.1.178:28800/api/v1/resource_pool/resources?is_online=true&entity_kind=equipment&limit=100
  ```
  若无 online 车辆，回退：
  ```http
  GET http://25.11.1.178:28800/api/v1/resource_pool/resources?entity_kind=equipment&limit=100
  ```
- **资源池返回**：equipment 资源列表，含 `resource_id / resource_name / resource_type / online_status / model_type` 等。
- **后端数据转换**：
  1. `_infer_vehicle_type` 把 `resource_type` / `model_type` 映射为内部车型（Fire-Support-UGV / Recon-Strike-UGV / Patrol-UGV / Electronic-UGV / Air-Ground-UAV）；
  2. 按车型填充 `supported_action_types`；
  3. 资源池不可达时返回本地 fallback 五型车。
- **返回前端结构**：
  ```json
  {
    "code": 200,
    "data": {
      "items": [
        {
          "vid": "equipment:XL01",
          "resource_type": "Fire-Support-UGV",
          "resource_name": "火力车-01",
          "display_name": "火力车",
          "supported_action_types": ["Auto-Move", "Lens-Recon", "7.62mm-Gun-Shot"]
        }
      ],
      "total": 1
    }
  }
  ```
- **完成功能**：
  - 从资源池服务获取在线车辆，映射为前端需要的车型结构。

### 4.4 资源池查询（路线 / 区域 / 目标）

#### 4.4.1 按类型查询本地资源池

- **前端调用时机**：
  - `ActionParamDialog` 挂载时并行加载 `ROUTE`、`AREA`、`TARGET` 三类资源。
- **前端接口**：
  ```http
  GET /api/v1/resources/by_type/{taskType}?limit={limit}
  ```
- **后端处理函数**：`list_resources_by_type` → `task_pool.query(task_type=task_type.upper(), limit=limit)`
- **后端向数据服务器发起的二次请求**：
  当前后端实现中 `task_pool.query` 会调用：
  ```http
  POST http://25.11.1.178:28801/api/v1/task_pool/resources/query
  Content-Type: application/json

  { "task_type": "ROUTE", "limit": 50 }
  ```
  （`taskType` 也可能是 `AREA` / `TARGET` / `EQUIPMENT`）
- **数据服务器返回**：对应类型资源数组。
- **后端数据转换**：目前直接透传资源项，前端自行解析 `points / polygon / location`。
- **返回前端结构示例（ROUTE）**：
  ```json
  {
    "code": 200,
    "data": {
      "items": [
        {
          "resource_id": "route:ROUTE_001",
          "title": "路线1",
          "points": [
            { "lon": 116.13, "lat": 39.766, "alt": 55, "radius": -1, "type": 1 }
          ]
        }
      ],
      "total": 1
    }
  }
  ```
- **完成功能**：
  - 为参数编辑提供路线、区域、目标资源选择。

### 4.5 行动参数编辑

#### 4.5.1 协同席：更新单个行动参数

- **前端调用时机**：
  - 用户双击行动卡片打开 `ActionParamDialog`；
  - 编辑参数后点击"保存"。
- **前端接口**：
  ```http
  PATCH /api/v1/action-sequences/plans/{planId}/actions/{actionId}
  Content-Type: application/json

  { "param": { ... } }
  ```
- **后端处理函数**：`patch_action_param` → `update_action_param`
- **关键说明**：
  - 数据服务器目前**不支持**直接 PATCH `/resources/{rid}/actions/{actionId}`，也不支持通过 PATCH `/resources/{rid}` 保存嵌套 `team_actions`；
  - 因此后端**只更新本地 `task_pool` 缓存**，并标记 `local_dirty=True`。
- **后端实际执行流程**：
  1. 若本地没有该 plan，先调用数据服务器补缓存：
     ```http
     GET http://25.11.1.178:28801/api/v1/task_pool/resources/simple/plan:{planId}
     ```
  2. 在本地 `plan.stages[].team_actions` 中找到对应 `action_id`，更新 `param`；
  3. 设置 `plan["local_dirty"] = True`，写回本地 `task_pool`。
- **返回前端结构**：
  ```json
  { "code": 200, "data": { "plan_id": "...", "action_id": "...", "updated": true } }
  ```
- **持久化说明**：
  - 若要让修改落盘到数据服务器，需要后续调用 `syncOperatorPlanToDataServer`（操控端）或在 PATCH plan 时由 `update_plan` 自动同步（协同席）。
- **完成功能**：
  - 支持在线编辑行动参数，本地缓存优先，等待后续同步。

#### 4.5.2 操控端：更新单个行动参数

- **前端接口**：
  ```http
  PATCH /api/v1/action-sequences/operator/plans/{planId}/actions/{actionId}
  ```
- **后端处理函数**：`patch_operator_action_param` → `update_operator_action_param`
- **后端向数据服务器发起的二次请求**：
  ```http
  GET http://25.11.1.56:28801/api/v1/task_pool/resources/simple/plan:{planId}
  ```
  仅用于本地无缓存时补全，不直接修改数据服务器。
- **后续前端同步**：
  - 成功后前端调用 `syncOperatorPlanToDataServer(planId)`，后端会把本地 plan 全量 import 到操控席数据服务器。
- **完成功能**：
  - 操控端本地编辑参数，最终通过 `sync` 持久化到数据服务器。

### 4.6 方案新建 / 编辑 / 追加

#### 4.6.1 操控端：新建行动序列方案

- **前端调用时机**：
  - 用户点击"新建"，在 `ActionSequenceCreator` 中保存。
- **前端接口**：
  ```http
  POST /api/v1/action-sequences/operator/plans
  Content-Type: application/json

  { "resource_id": "plan:PLAN_xxx", "task_type": "PLAN", "plan_id": "PLAN_xxx", "stages": [...] }
  ```
- **后端处理函数**：`create_plan_operator` → `create_operator_plan`
- **后端向数据服务器发起的二次请求**：
  ```http
  POST http://25.11.1.56:28801/api/v1/task_pool/ingestion/import
  Content-Type: application/json

  {
    "resources": [{ ...plan 完整对象... }],
    "return_data_type": "typed",
    "ignore_errors": true
  }
  ```
- **后端实际执行流程**：
  1. 补全 `resource_id / task_type / created_at / updated_at / lifecycle`；
  2. 尝试 `import_plan_to_operator` 导入操控席数据服务器；
  3. 无论导入成败，都保存到本地 `task_pool`。
- **返回前端结构**：
  ```json
  { "code": 200, "data": { "plan_id": "PLAN_xxx", "resource_id": "plan:PLAN_xxx", "title": "...", "state": "DRAFT" } }
  ```
- **完成功能**：
  - 在操控端本地创建新方案，并尝试导入数据服务器。

#### 4.6.2 协同席/操控端：编辑已有方案

- **前端接口**：
  ```http
  PATCH /api/v1/action-sequences/plans/{planId}          // 协同席
  PATCH /api/v1/action-sequences/operator/plans/{planId} // 操控端
  ```
- **后端处理函数**：
  - 协同席：`patch_plan` → `update_plan` → `update_plan_locally` + `sync_plan_to_data_server`
  - 操控端：`patch_plan_operator`
- **后端实际执行流程（协同席）**：
  1. 用白名单字段（`title / description / state / teams / targets / stages / search_text / car_actions / vehicle_summary`）更新本地 `task_pool`；
  2. 标记 `local_dirty=True`；
  3. 调用同步逻辑，把本地 plan 全量 import 到协同席数据服务器：
     ```http
     POST http://25.11.1.178:28801/api/v1/task_pool/ingestion/import
     Content-Type: application/json

     {
       "resources": [{
         "resource_id": "plan:{planId}",
         "task_type": "PLAN",
         "plan_id": "{planId}",
         "title": "...",
         "description": "...",
         "state": "DRAFT",
         "teams": [...],
         "targets": [...],
         "stages": [...]
       }],
       "return_data_type": "typed",
       "ignore_errors": true
     }
     ```
  4. 同步成功后立即拉取数据服务器最新数据：
     ```http
     GET http://25.11.1.178:28801/api/v1/task_pool/resources/simple/plan:{planId}
     ```
  5. 更新本地缓存并清除 `local_dirty`。
- **操控端差异（已更新）**：
  - **不再仅更新本地 task_pool**，而是直接使用请求体作为完整 plan 数据，调用操控席数据服务器 `/ingestion/import` 全量保存，确保 `stages/team_actions` 等嵌套数据正确落盘；
  - 保存成功后返回更新后的 plan 详情。
- **完成功能**：
  - 修改已有方案中某辆车的全部行动序列；协同席直接同步到数据服务器，操控端也直接保存到数据服务器。

#### 4.6.3 协同席/操控端：追加车辆行动序列

- **前端接口**：同 4.6.2 的 `PATCH`。
- **后端处理**：与编辑一致，`buildAppendedPlan` 在已有 plan 中新增车辆/actions，然后走 `update_plan_locally` + 同步。
- **完成功能**：向现有方案中追加一辆新车的行动序列。

### 4.7 方案同步

#### 4.7.1 操控端：本地 plan 同步到数据服务器

- **前端调用时机**：
  - 操控端保存/编辑/追加参数后；
  - 操控端删除车辆行动序列后。
- **前端接口**：
  ```http
  POST /api/v1/action-sequences/operator/plans/{planId}/sync
  ```
- **后端处理函数**：`sync_plan_operator` → `sync_plan_to_operator` → `sync_plan_to_data_server(_http_post_operator, _http_get_operator, label="operator")`
- **后端向数据服务器发起的二次请求**：
  1. 全量 import：
     ```http
     POST http://25.11.1.56:28801/api/v1/task_pool/ingestion/import
     Content-Type: application/json

     {
       "resources": [{ "resource_id": "plan:{planId}", "task_type": "PLAN", ... }],
       "return_data_type": "typed",
       "ignore_errors": true
     }
     ```
  2. import 成功后立即拉取最新：
     ```http
     GET http://25.11.1.56:28801/api/v1/task_pool/resources/simple/plan:{planId}
     ```
- **后端本地状态变更（已更新）**：
  - **本地 task_pool 无缓存时，先从数据服务器拉取 plan 并缓存，再执行同步**，避免 sync 接口返回 500；
  - 同步成功 → 更新本地缓存，清除 `local_dirty`；
  - 拉取失败 → 保留 `local_dirty=true`，后续 `get_plan_detail` 继续优先本地数据。
- **返回前端结构**：
  ```json
  { "code": 200, "data": { "plan_id": "...", "action": "sync_to_operator", "message": "方案已同步到数据服务器" } }
  ```
- **完成功能**：
  - 把操控端本地修改持久化到数据服务器，并刷新本地缓存。

### 4.8 Zenoh 通知 + SSE 实时刷新（替代轮询）

#### 4.8.1 后端订阅 Zenoh plan 变化主题

- **订阅主题**：
  - `op/pool/task/plan/update`：plan 内容/嵌套资源任意字段变化
  - `op/pool/task/plan/count`：plan 新增/删除
- **报文格式**：
  ```json
  { "plan_id": "plan-1021" }
  { "plan_id": "plan-1021", "operation": "add" }
  ```
- **后端处理**：收到通知后通过 SSE 推送给前端，**不直接返回 plan 数据**，前端收到通知后调用现有 API 刷新。

#### 4.8.2 SSE 事件流接口

- **前端接口**：
  ```http
  GET /api/v1/action-sequences/events
  ```
- **推送事件**：
  - `action_sequence.plan.updated`：plan 内容变化，payload `{"plan_id": "xxx"}`
  - `action_sequence.plan.count_changed`：plan 新增/删除，payload `{"plan_id": "xxx", "operation": "add"/"delete"}`
  - `system.heartbeat`：心跳，每 30 秒一次
- **前端处理**：
  - 收到 `plan.updated`：若当前选中该 plan，调用 `refreshDetail(planId)` 刷新详情；同时 `loadPlans(true)` 静默刷新列表；
  - 收到 `plan.count_changed`：`loadPlans(true)` 刷新列表；若删除的是当前选中 plan，清空选中；
  - EventSource 自动重连，组件卸载时关闭连接。

#### 4.8.3 与原轮询方式的对比

| 方式 | 延迟 | 服务器压力 | 实时性 |
|------|------|-----------|--------|
| 原 5 秒轮询 | 最大 5 秒 | 高（每 5 秒全量查询） | 差 |
| Zenoh + SSE | 秒级 | 低（仅变化时通知） | 好 |

### 4.9 方案下发

#### 4.9.1 协同席：下发到操控席数据服务

- **前端接口**：

- **完成功能**：
  - 把协同席方案通过 import 方式下发到操控席数据服务器。

#### 4.9.2 协同席：按席位转发方案

- **前端接口**：

- **后端处理函数**：`dispatch_plan_forward_route` → `dispatch_plan_forward` → `forward_resources_to_targets`
- **后端向数据服务器发起的二次请求**：
  ```http
  POST http://25.11.1.178:28801/api/v1/task_pool/ingestion/forward

    "target_ips": ["1", "2"],

    "timeout_seconds": 30
  }
  ```

- **数据服务器返回**：转发结果（成功/失败的目标 IP 列表）。
- **返回前端结构**：

- **完成功能**：
  - 通过协同席数据服务器 `/ingestion/forward` 把方案下发到指定操控席位。

#### 4.9.3 操控端：下发到无人车（Zenoh send_mission）

- **前端接口**：
  ```http
  POST /api/v1/action-sequences/operator/plans/{planId}/dispatch
  Content-Type: application/json

  { "vehicle_vid": "XL01" }
  ```
- **后端处理函数**：`dispatch_plan_operator`
- **后端实际执行流程**：
  1. 先调用 `sync_plan_to_operator(planId)` 把本地 plan 同步到操控席数据服务器（见 4.7.1）；
  2. 调用 `get_plan_detail_operator(plan_id)` 获取最新 plan；
  3. 去掉 `equipment:` 前缀；
  4. `build_mission_payload` 将 plan 转换为 MissionService `send_mission` 格式：
     - `service`: "MissionService"
     - `action`: "send_mission"
     - `args.mission_data.task`: 含 `tid / type / cnt / start / end / vehicles`
     - 每个 action 通过 `_build_service_from_action` 转换为 `sid + param` 的服务对象；
  5. 通过 Zenoh 发布到 topic：`op/t01/g01/v{vid}/cmd/MissionService/send_mission`
- **返回前端结构示例**：
  ```json
  {
    "code": 200,
    "data": {
      "plan_id": "...",
      "vehicle_vid": "XL01",
      "topic": "op/t01/g01/vXL01/cmd/MissionService/send_mission",
      "mission_tid": "..."
    }
  }
  ```
- **完成功能**：
  - 把行动方案通过 Zenoh 真正下发到无人车执行。

### 4.10 车辆行动序列删除

#### 4.10.1 协同席 / 操控端：删除指定车辆行动序列

- **前端接口**：
  ```http
  POST /api/v1/action-sequences/plans/{planId}/vehicles/{vid}/delete          // 协同席
  POST /api/v1/action-sequences/operator/plans/{planId}/vehicles/{vid}/delete // 操控端
  ```
- **后端处理函数**：`delete_vehicle_from_plan` / `delete_vehicle_from_plan_operator` → `_delete_vehicle_from_plan`
- **后端向数据服务器发起的二次请求**：
  1. 收集该车辆在 `stages.team_actions` 和 `plan.car_actions` 中的所有 `car_actions` 资源 ID；
  2. 对每个 `car_actions:{xxx}` 调用级联删除：
     ```http
     POST http://25.11.1.178:28801/api/v1/task_pool/resources/{car_actions_rid}/delete
     Content-Type: application/json

     { "cascade": true }
     ```
     （操控端为 `25.11.1.56:28801`）
  3. 数据服务器返回 `deleted_resource_ids`，其中 `action:` 开头的 ID 被收集为 `deleted_actions`；
  4. 更新本地 `task_pool`：移除该车辆；
  5. 调用 `sync_plan_to_data_server` 把更新后的 plan 重新 import 到数据服务器。
- **返回前端结构**：
  ```json
  {
    "code": 200,
    "data": {
      "ok": true,
      "plan_id": "...",
      "vid": "equipment:XL01",
      "deleted_actions": ["action:..."],
      "deleted_car_actions": ["car_actions:..."],
      "sync_ok": true
    }
  }
  ```
- **完成功能**：
  - 从数据服务器级联删除指定车辆的 car_actions 及其子 actions，并同步更新 plan。

### 5.2 坐标提取规则

`ActionSequencePanel.vue` 中 `extractCoordinates(param)` 按以下优先级提取可绘制坐标：

1. `param.waypoints`（列表）
2. `param.target.location`（列表，Lens-Recon 多边形）

统一输出：

```ts
{ lon: number; lat: number; alt: number }[]
```

### 5.3 断连策略转换

| UI 显示 | UI 值 | 后端协议数字 |
|---|---|---|
| 继续 | `"continue"` | `2` |
| 停车 | `"stop"` | `0` |
| 返航 | `"return"` | `1` |

### 5.4 action_type 推断链

当数据服务器返回的 `action_type` 为空或脏数据时，后端/前端按以下优先级推断标准类型：

1. `action_id` 语义推断（如 `auto-move` / `CH_RETURN` / `FS_LENS`）
2. `param` 结构推断（如 `frequency` → `em-recon` / `em-interference`）

## 7. 异常处理

- 所有接口统一走 `safeFetch`，8 秒超时返回 `{ ok: false, error: '请求超时' }`；
- 后端到数据服务器请求失败时返回 `None`，业务层回退到本地 `task_pool`；
- 失败时通过 `appendSystemMessage` 在聊天面板提示用户，不影响其它流程；
- 地图上图失败仅提示，不会阻止后续操作。
